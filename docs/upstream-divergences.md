# Upstream divergences

Running list of deliberate departures from `upstream/Foreman`, one line per divergence. Add to this file whenever a port task changes behavior instead of just moving code.

- `AppPaths.ExecutableDirectory` (`AppContext.BaseDirectory`) replaces `Application.StartupPath` in `DataCache.cs`, `ErrorLogging.cs`, and `PresetProcessor.cs`; WinForms isn't available on this target.
- `IconCache`, `IconCacheProcessor`, and `ForemanIconCacheFile` are ported to SkiaSharp: `SKBitmap` replaces `Bitmap`, and `SKCanvas`/`SKPath`/`SKImage` replace `Graphics`/`GraphicsPath`. The manual per-pixel blend math in `IconCacheProcessor.GetIconAndColor` is otherwise unchanged, since `SKColorType.Bgra8888` with `SKAlphaType.Premul` matches GDI+'s `Format32bppPArgb` byte layout (B, G, R, A).
- `IconCacheProcessor.GetIconAndColor` drops the final premultiplied-to-non-premultiplied conversion GDI+ needed only to work around a WinForms rendering quirk; icons stay `SKAlphaType.Premul` throughout, since Skia can only render onto premultiplied or opaque targets, never non-premultiplied ones. `GetAverageColor` un-premultiplies each sampled pixel inline instead, so the averaged color still matches upstream's intent, and `AddBorder`'s border-fill bytes are the premultiplied equivalent of the original gray-at-quarter-alpha color.
- `IconCacheProcessor.CombinedQualityIcon`'s composition canvas is always `SKAlphaType.Premul`, rather than mirroring the source icon's pixel format like upstream did, for the same rendering-target reason.
- `IconCache.LoadIconCache`'s `UserMessages.Show(...)` MessageBox call on a corrupt cache file becomes `ErrorLogging.LogLine(...)` with the same message text, matching the pattern already used in `PresetExportFormat.ShowOutdatedWarningIfNeeded`.
- `ForemanIconCacheFile.ParsePayloadAsync` and `IconCacheProcessor.LoadImageFromMod`/`GetIcon` treat a `null` return from `SKBitmap.Decode` (Skia's decode-failure signal) as an exception, matching the exception GDI+'s `new Bitmap(...)` throws on the same failure so the surrounding try/catch behaves the same either way.
- Icon-typed members retyped from `System.Drawing.Bitmap` to `SkiaSharp.SKBitmap?`: `DataCache.NoBeaconIcon`, `DataCacheStore.ElectricityIcon`, and the five `*QualityPair.Icon` properties in `Models/QualityPairs.cs`. `DataObjectBase.Icon`/`IDataObjectBase.Icon` and `DataCache.UnknownIcon` went through the same `Bitmap` to `SKBitmap` retype but landed non-nullable (`SKBitmap`, no `?`); see the `Foreman.Core.csproj` quality-gates entry below for why.
- Serializer viewer-facing members removed (restored in UI project, phase 2+): `GraphSaveCodec.BuildViewer`, `WriteViewerToString`, `BuildNodeCopyOptions`, `WriteNodeCopyOptionsToString`; `GraphSaveWriter.WriteViewer`, `WriteViewerUi`, `WriteNodeCopyOptions` (and its only caller, the `SortEnabled` helper); `GraphSaveLoader.ToNodeCopyOptions`. All depend on `ProductionGraphViewer` / `NodeCopyOptions`, which live in the WinForms `ProductionGraphView/` folder and aren't part of Foreman.Core.
  `GraphSaveCodec.ReadViewer` and `GraphSaveReader.ReadProductionGraphViewer` were cut in the same pass but didn't belong on this list: neither touches a UI type (`GraphViewerSaveDocument` is a plain Core record), so a later fix-wave restored both along with `ReadGraphPayload`'s viewer-fallback branch (a real `.fjson` save file is a viewer document, not a bare graph fragment, so `ReadGraphPayload` needs the fallback to load any real save at all).
- `Preset` (the `name`/`isCurrentlySelected`/`isDefaultPreset` data class) extracted verbatim from upstream `Forms/MainForm.cs` into `src/Foreman.Core/Preset.cs`. `DataCache`, `PresetProcessor`, and `InfoPackageClasses` need the type; `MainForm.cs` itself stays a UI-only file and isn't copied.
- `PresetExportFormat.ShowOutdatedWarningIfNeeded`: the `UserMessages.Show(...)` MessageBox call is now `ErrorLogging.LogLine(...)` with the same message text; `UserMessages.cs` is UI-only and excluded from Core.
- `FactorioPathsProcessor.cs` retargeted at macOS: install-location search now checks `/Applications/factorio.app/Contents` and `~/Applications/factorio.app/Contents` instead of the registry and Program Files; the Steam library scan points at `~/Library/Application Support/Steam/steamapps/libraryfolders.vdf` with a `factorio.app/Contents` suffix per library; the `__PATH__system-write-data__` mapping resolves to `~/Library/Application Support/factorio` instead of `%appdata%\Factorio`; executable and install-path checks look for `Contents/MacOS/factorio` instead of `bin/x64/factorio.exe`. `GetFactorioInstallLocations` and `GetFactorioUserPath` each gained an optional `homeOverride` parameter (upstream had none to diverge from, since the Windows version reads the registry rather than a home-relative path) so tests can point both at a fixture tree instead of the real home directory; every existing call site omits it and keeps hitting the real machine. Task 5 pinned this file's behavior with tests, then a fix round corrected a real gap the tests exposed: `config-path.cfg` turns out to be a Windows/standalone-only concept, absent from every real macOS bundle (confirmed against a real Steam-installed, repeatedly-launched Factorio on the port machine), so gating install detection and user-data resolution on that file meant neither could ever fire against a real macOS Steam install. Install detection now checks for the `Contents/MacOS/factorio` executable itself instead of `config-path.cfg`. `GetFactorioUserPath` still tries the `config-path.cfg` chain first, for a hypothetical custom install that does ship one, then falls back to reading `config.ini` directly from the fixed macOS user-data folder (`~/Library/Application Support/factorio/config/config.ini`) when `config-path.cfg` is absent, matching the real file confirmed on the port machine. That fallback's `config.ini` parse also fed the `config[12..newline]` finding below: `__PATH__executable__`/`__PATH__system-write-data__` prefixes are exactly 20/27 characters and self-check against their own length, but `write-data=` is 11, one short of the `config-path.cfg` first-line slice's magic number 12; the config-path.cfg-chain fixture pads that line with a trailing space to satisfy the existing arithmetic, since no real `config-path.cfg` was available on the port machine (it being a Windows/standalone-only file) to confirm the true byte format against.
- `FactorioPathsProcessor.GetFactorioUserPath`'s `verboseFail` branches: the `UserMessages.Show(...)` MessageBox calls become `ErrorLogging.LogLine(...)` with the same message text, the same substitution already applied throughout Core (see the `IconCache.LoadIconCache` and `PresetExportFormat.ShowOutdatedWarningIfNeeded` entries above).
- `Settings.cs`: removed `SettingChangingEventHandler`. It referenced `System.Configuration.SettingChangingEventArgs`, which needs a `ConfigurationManager` package reference we don't take; the handler was already dead code, never wired up without the `Settings.Designer.cs` file we don't copy.
- `tests/ForemanTest/support/ForemanTestBase.cs` and `ForemanTestAssemblySetup.cs`: the `UserMessages.TestHandler` guard is gone. `UserMessages.cs` is UI-only (`System.Windows.Forms.MessageBox`/`DialogResult`) and excluded from Foreman.Core; both of Core's former callers already log through `ErrorLogging.LogLine` instead of popping a dialog (see the `IconCache.LoadIconCache` and `PresetExportFormat.ShowOutdatedWarningIfNeeded` entries above), so there's nothing left to guard against. Both classes are kept as no-ops so the 17 test classes that derive from `ForemanTestBase` still compile.
- `tests/ForemanTest/support/GraphSaveTestUi.cs` is upstream's own `ForemanTest/support/GraphSaveTestUi.cs`, edited, not a helper invented for the port. `Foreman.Core.csproj` gained `<InternalsVisibleTo Include="ForemanTest" />` (mirroring `Foreman.csproj` upstream) so the test project can reach Core's internal serializer types. Its `ReadViewer` method briefly reimplemented `GraphSaveCodec.ReadViewer` by hand while that method was missing from Core (see the `GraphSaveCodec.BuildViewer` entry above); now that `ReadViewer` is restored, `GraphSaveTestUi.ReadViewer` is a one-line delegation to it again.

Upstream's `ForemanTest.csproj` links these in directly from a sibling `Foreman/Presets/` folder that doesn't exist in our layout (no UI project checked out yet); without this folder, `VanillaDataCacheFixture`/`SpaceAgeDataCacheFixture`-gated tests in `DataCacheTests`, `FluidMiningExportTests`, `FlowchartLoadTests`, and `ProductionGraphSessionCoverageTests` would report `Assert.Inconclusive` instead of exercising real Core logic.

Every test that used it (`BeaconElementDrawTests`, `ChooserLayoutTests`, `DataCacheAvailabilityFixpointTests`, `ProductionGraphViewerEditTests`, `SettingsFormEnabledObjectsTests`) is UI-only and wasn't copied, so its `Thread.SetApartmentState(ApartmentState.STA)` call (a Windows-only concept) stays dormant rather than needing a no-op rewrite; revisit if a later phase's UI tests bring it back into use.
- `tests/ForemanTest/GraphSaveSerializerTests.cs` (upstream's `GraphSaveCodecTests`): ported, minus two tests, `GraphSaveCodec_ReadNodeCopyOptions_MatchesSerializedPayload` and `SerializeNodeCopyOptions_RoundTrip_RestoresAssemblerAndModules`. The other 13 tests needed only a `using Foreman.ProductionGraphView;` line dropped; four of them (the ones touching `GraphSaveCodec.ReadViewer`) needed that method restored first (see the `GraphSaveCodec.BuildViewer` entry above).
- `tests/ForemanTest/ErrorLoggingTests.cs` and `PresetExportFormatTests.cs`: ported. `ErrorLoggingTests` swaps `Application.StartupPath` for `AppPaths.ExecutableDirectory` (see the first entry in this file). `PresetExportFormatTests`'s two `ShowOutdatedWarningIfNeeded` tests swap the `UserMessages.UseHandler` MessageBox capture for reading `errorlog.txt` after `ErrorLogging.ClearLog()`, matching the `UserMessages.Show` to `ErrorLogging.LogLine` substitution `PresetExportFormat` itself already made (see that entry above); the assertions (message text present or absent) are otherwise the same.
- `src/Foreman.Core/Graphics/`: added, holding the same ten `.png` files upstream ships as `Content` in `Foreman.csproj` (`BurnerGeneratorIcon`, `ElectricityIcon`, `ErrorIcon`, `ExtraGroupIcon`, `HeatIcon`, `PlantAssembler`, `PlayerAssembler`, `RocketAssembler`, `SpoilAssembler`, `UnknownIcon`), each a `Content`/`PreserveNewest` item in `Foreman.Core.csproj` too (forward-slash paths, since this is a cross-platform project file now). Without them, every `IconCache.GetIcon`/`DataCache`/`DataCacheBootstrap` call that loads one of these bundled icons decode-fails and falls back to a blank bitmap, logging an `IconCache.GetIcon failed` line each time (3,941 times in one full test run before this fix). `NoBeaconIcon` in `DataCache.cs` references a `Graphics/NoBeacon.png` that was never part of upstream's shipped set either (no such file exists anywhere in `upstream/Foreman`), so it still decode-fails on both platforms; that one predates the port and is out of scope here. `ErrorIcon.png` isn't read by any Core code today (its one upstream caller, `ErrorNoticeElement`, is UI-only) but is included anyway for parity with upstream's Content set, ready for the UI project.
- `Foreman.Core.csproj` gained upstream's quality gates (`TreatWarningsAsErrors`, `AnalysisLevel=latest-recommended`, `EnableNETAnalyzers`, `EnforceCodeStyleInBuild`), matching `Foreman.csproj`/`ForemanTest.csproj`. `GenerateDocumentationFile` stays `false` (upstream has it `true`), the same choice `ForemanTest.csproj` already made, to avoid a forced pass of XML doc comments across every public Core member. Turning these on surfaced two `CS8602` warnings in `EntityDataLoader.cs` (`ingredient.Icon.Height`, on the `BoilerAdditionalProcessing` and `GeneratorAdditionalProcessing` recipe-icon paths); `IconCache.GetIcon`/`CombineIcons`/`UnknownIcon` never actually return `null` (the catch paths always construct a blank `SKBitmap` instead), so the real fix is retyping that chain as non-nullable rather than adding a null check or a `!`: `IconCache.GetIcon`/`CombineIcons`/`UnknownIcon`, `DataCache.UnknownIcon`, and `DataObjectBase.Icon`/`IDataObjectBase.Icon` are now `SKBitmap`, not `SKBitmap?`. `IconColorPair.Icon` stays nullable; `IconCacheProcessor` legitimately builds a null-icon pair when a mod icon can't be resolved, and `DataObjectBase.SetIconAndColor` coalesces that against `DataCache.UnknownIcon` before it ever reaches `Icon`. No other analyzer findings came up.
- `IconCacheProcessor.cs`: `SKCubicResampler.Mitchell` (`HighQualitySampling`) and `IconCache.cs`'s `SKFilterMode.Linear` (`BilinearSampling`) are Skia's closest equivalents to GDI+'s `InterpolationMode.HighQualityBicubic` and `HighQualityBilinear`; the resampling math isn't identical between the two graphics stacks, so scaled icon output can differ at the pixel level from a Windows build, though not visibly.
- `IconCacheProcessor.LoadImageFromMod`'s path normalization (folder- and zip-mod icon lookups): upstream hardcodes `\` as the separator because Windows is the only target, and it's paired with `Path.Combine`'s implicit native separator on the archive-key build side (`CreateIconCache`'s zip-entry indexing), so both sides agreed. Ported as-is, this normalized to a hardcoded `\` while the archive-key build side's `Path.Combine` switched to macOS's native `/`, so folder-mod icon files got literal-backslash filenames (decode fails, since macOS doesn't treat `\` as a separator) and zip-mod lookups never matched their keys. Fixed by normalizing to `Path.DirectorySeparatorChar` on the lookup side instead of a hardcoded `\`, so both sides agree on whichever separator is native to the running OS, matching upstream's Windows behavior and fixing macOS.
- `FactorioPathsProcessor.GetFactorioInstallLocations`'s Steam-library scan tries `steamapps/common/Factorio/factorio.app/Contents` (capitalized, matching upstream's assumption) before falling back to lowercase `.../common/factorio/factorio.app/Contents`. Steam's own install folder for Factorio is lowercase; a case-insensitive APFS volume (the default) resolves either spelling to the same directory, but a case-sensitive one won't, so the fallback is real coverage there, not just defensive.
- `FactorioInstallValidator.TryValidateExecutable`: `System.Diagnostics.FileVersionInfo` reads PE version resources and is always empty for a Mach-O binary, so every real macOS Factorio install was rejected as version `0.0.0.0`. Now tries `Contents/Info.plist` first (`CFBundleShortVersionString`, falling back to `CFBundleVersion`, parsed as a plain `major.minor.build` split, no plist library dependency) and only falls back to `FileVersionInfo` for a non-bundle layout (a bare `factorio.exe`, if one is ever pointed at directly).
- `ForemanIconCacheFile.EncodePng`: `SKBitmap.Encode(...)` returning `null` (Skia's encode-failure signal, distinct from the decode-failure `null` handled elsewhere) now throws `InvalidDataException` instead of letting the write path null-ref on `.ToArray()`, matching how every decode failure in this file is already handled.
- `IconCacheProcessor.GetIconAndColor`'s tail (average-color calculation, optional `AddBorder` pass, final `IconColorPair` construction) is wrapped in upstream's `try`/`finally` again; without it, an exception thrown by `GetAverageColor` or `AddBorder` would leak the composed `SKBitmap` instead of disposing it, a straight port gap rather than a platform difference.
- `[Serializable]` on `IconColorPair` was dropped; nothing in Core uses binary serialization, and `SKBitmap` (unlike GDI+'s `Bitmap`) isn't `[Serializable]` either, so keeping the attribute would just be inert.
- `Foreman.Mac.Services.AppSettings`/`SettingsService` replace `Properties.Settings` (`ApplicationSettingsBase`, backed by Windows `user.config`) with a plain POCO written to `~/Library/Application Support/Foreman/settings.json` via `System.Text.Json`, `WriteIndented`, enums as strings; every property name and default is copied verbatim from `Settings.Designer.cs`, except `DefaultModuleOption`, `DefaultAssemblerOption`, `DefaultRateUnit`, and `DefaultNodeDirection`, which are typed as their real Foreman.Core enums (`ModuleSelector.Style`, `AssemblerSelector.Style`, `ProductionGraph.RateUnit`, `NodeDirection`) instead of upstream's raw `int`, since those enums already exist in Core; `LevelOfDetail`, `AnnotTextFontStyle`, `AnnotTextAlign`, and `AnnotShapeType` stay `int` because their upstream enums (`ProductionGraphViewer.LOD`, `System.Drawing.FontStyle`/`StringAlignment`, the UI-only `ShapeType`) aren't ported to Core yet. `CurrentPresetName`'s upstream default is `""`, not `"Factorio 2.0 Vanilla"`; `MainForm.cs`'s `DefaultPreset` constant and its `NewGraph`/`GetValidPresetsList` fallbacks are what actually land it on `"Factorio 2.0 Vanilla"` at runtime, so this port keeps the verbatim empty default and defers that fallback behavior to whichever task ports `MainForm`.
- `AppSettings.UpgradeRequired` is dead in this port: upstream's `Program.UpgradeUserSettingsIfNeeded` reads it to decide whether to copy settings forward from a previous assembly version's `user.config` folder, a concept JSON settings don't have (there's only ever one `settings.json`, at a fixed path, with no per-version folder to migrate from). Kept for file-format fidelity with `Settings.Designer.cs` only; nothing in the port reads or writes it.
- `Foreman.Mac.Views.DataLoadWindow` ports `Forms/DataLoadForm.cs`. `DataCache(Properties.Settings.Default.UseRecipeBWfilters)` becomes `DataCache(filterRecipes)`, a `DataLoadWindow(Preset preset, bool filterRecipes = true)` constructor parameter (the `true` default matches `AppSettings.UseRecipeBWfilters`'s own default); whichever task threads `AppSettings` into the boot path passes the live setting instead of relying on the default. A public parameterless constructor (delegating to an empty `Preset`) was added purely so the Avalonia XAML compiler doesn't warn about an unreachable design-time loader; nothing in the app calls it.
- `Foreman.Mac.Canvas.GraphCanvasControl` (phase 5a task 1, floating-panel host primitive): base type changes from `Control` to `Decorator`, with a plain `Avalonia.Controls.Canvas` set as its `Child` and passed to the new `FloatingPanelHost`. Upstream's `FloatingTooltipControl` panel half adds the edit panel as a genuine sibling `Control` of `ProductionGraphViewer` (`parent.Controls.Add(control)`), getting real WinForms mouse/keyboard/focus routing for free; Avalonia has no such "arbitrary sibling control with independent Z-order and hit-testing" primitive on a plain `Control`, and the natural equivalent, making `GraphCanvasControl` itself a `Canvas` so floating panels sit in its own `Children` collection, doesn't work here because `Avalonia.Controls.Panel.Render(DrawingContext)` is sealed, and `GraphCanvasControl`'s Skia surface paints through exactly that override (`Render(DrawingContext)` calling `context.Custom(new DrawOperation(...))`). `Decorator.Render` is not sealed (only `Border`, a different `Decorator` subclass, seals its own), so `GraphCanvasControl` keeps painting Skia through its own `Render(DrawingContext)` override unchanged, while the `Decorator.Child` canvas gets real Avalonia layout, focus, and hit-testing for whatever `FloatingPanelHost.Show` mounts into it. Since the overlay canvas is a `Decorator.Child` (a real Avalonia visual-tree parent-child relationship, not a sibling), a routed pointer/key event on the panel still bubbles up through `GraphCanvasControl` itself; `OnPointerPressed`/`OnKeyDown`/`OnKeyUp` gate on `FloatingPanelHost.IsOpen`/`Bounds` explicitly instead of relying on WinForms' automatic "a covered sibling control absorbs the click before the parent ever sees it" behavior.
- `Foreman.Mac.Canvas.Panels.EditPanelViewportLayout.Apply`: the natural-size-then-clamp arithmetic is a verbatim port of upstream's `EditPanelViewportLayout.Apply`, but the `AutoScroll`-backed scroll host (`EnsureScrollHost`/`LayoutScrollableContent`, WinForms `Panel.AutoScroll`) has no Avalonia port yet. Task 1 validates the host against a fixed-size placeholder panel with nothing to overflow; a real `ScrollViewer` wrapper for oversized panel content is deferred to whichever later panel first needs one (most likely `EditRecipePanel`, phase 5a step 5).
- `Foreman.Mac.Canvas.Panels.FloatingPanelHost`'s click-outside-closes behavior (phase 5a task 1): upstream's `ProductionGraphViewer_MouseDown` calls `ToolTipRenderer.ClearFloatingControls()` unconditionally as its first statement, closing every open tooltip-hosted panel regardless of click location, then still runs the rest of its own click handling (node hit-test, selection, drag-origin) on that same click - a closing click is never swallowed from also acting on the canvas upstream, only a click that lands *on* the panel itself never reaches `ProductionGraphViewer_MouseDown` at all, since the panel is a real WinForms child control in front of it. This port matches both halves exactly: `GraphCanvasControl.OnPointerPressed` closes the panel unconditionally when the click falls outside `FloatingPanelHost.Bounds` and then falls through to its normal click handling unchanged, and returns early (without touching selection/drag state) only when the click falls inside those bounds.
- `Foreman.Mac.Canvas.GraphCanvasControl`'s canvas-shortcut suspension while a panel is open (phase 5a task 1): upstream's `SubwindowOpen` only gates the WASD pan shortcuts (`ProductionGraphViewer_KeyDown`'s `Keys.W`/`A`/`S`/`D` branches). This port generalizes that to every canvas shortcut: `OnKeyDown`/`OnKeyUp` return immediately whenever `FloatingPanelHost.IsOpen`, before reaching clipboard, movement, or delete handling, since a real Avalonia child control receiving focus (unlike upstream's decorative-tooltip-turned-real-panel split) means every canvas shortcut is a plausible collision, not just WASD. `Escape` is carved out of the early return specifically to close the panel, mirroring upstream's own `Escape`-cancels-`inDrawShapeMode` case immediately below it.
- `Foreman.Mac.Views.DataLoadWindow.OnClosing`'s "preset loading is still in progress" warning: Avalonia has no built-in `MessageBox`, so `Foreman.Mac.Dialogs.ShowWarningAsync` (a small owned modal `Window`, `Views/MessageDialog.axaml`) replaces `UserMessages.Show(...)`, with `ErrorLogging.LogLine(...)` of the same message kept alongside it, matching the logging substitution used everywhere else in this port. Upstream shows the MessageBox synchronously inside `FormClosing` and lets the close proceed once dismissed; Avalonia's `Closing` has no synchronous blocking equivalent, so the port cancels the first close attempt (`e.Cancel = true`), shows the dialog asynchronously, and re-closes once the user dismisses it. In the (usual) case where the background load finishes while the dialog is still open, `RunLoadAsync`'s own completion `Close()` call goes through unblocked, since by then `loadInProgress` is already false. In practice this means the window closes as soon as the load finishes even if the warning dialog is still up. Given preset loads are seconds long and the warning only fires when the user closes mid-load, this is a close enough approximation of upstream's observable order (warn, then close) without literally blocking the UI thread. `CloseWarningMessage`'s text no longer copies upstream's "may use an incomplete set of items and recipes" wording, because it isn't true for this port: `ShellBootstrapper`'s `LoadPresetAsync` awaits `DataLoadWindow.LoadTask` to completion regardless of whether the user closes the window early, so `MainWindow` only ever receives a fully loaded cache. Upstream's version of this hazard is real, since `ProductionGraphViewer.LoadPreset` reads `form.GetDataCache()` the instant `ShowDialog()` returns, and WinForms' `ShowDialog()` unblocks as soon as `Close()` runs, whether or not the orphaned `async void` load behind it has actually finished. The port's message instead says what actually happens here: closing the window does not stop the load, which keeps running in the background, and the shell finishes setting up once it completes. A close that truly aborts the load, rather than merely detaching the window from it, would need `DataCache.LoadAllData` to accept a `CancellationToken`; Core doesn't offer one today, so real abort parity with upstream is deferred to whichever task adds that support.
- `AppSettings.FlagDarkMode` widened from upstream's `bool` to a `Foreman.Mac.Services.ThemeMode { System, Light, Dark }` enum, since Avalonia's `RequestedThemeVariant` is itself tri-state and upstream's on/off toggle has no "follow the OS" option to map onto. `SettingsService` gained a `ThemeModeJsonConverter` that reads a legacy bool value (`false`→`System`, `true`→`Dark`) alongside the normal enum-as-string form, so an existing `settings.json` from before this change upgrades in place instead of tripping the corrupt-file catch and losing every other setting to defaults. CORRECTION (human nit fix): `SettingsWindow.CommitGraphOptionsTab` originally committed `ThemeMode.System` when "Enable Dark Mode" was left unchecked, so an OS already in dark appearance stayed dark after unchecking it - upstream's `SetDarkMode`/`SetLightMode` pair (`MainForm.cs:36-46`) is strictly binary, with no OS-follow branch. The checkbox now commits `Light` on uncheck to match that binary contract exactly. `ThemeMode.System` stays reachable only as `AppSettings`'s own default (a fresh install, or an old `settings.json` upgraded through the legacy-bool convertor above) - it's a cold-start value with no UI control that can set it once Settings has been opened and confirmed even once.
- `Foreman.Core.csproj` gained `<InternalsVisibleTo Include="Foreman.Mac" />` and `<InternalsVisibleTo Include="Foreman.Mac.UiTests" />`, so `MainWindow`'s `VersionLabel` can read the internal `AppVersion` class. `AppVersion` stayed `internal` rather than going `public`: it already has one friend assembly (`ForemanTest`) for exactly this reason, so adding the shell's two assemblies to that same list is consistent with the pattern instead of widening Core's public surface for a single label.
- `Foreman.Mac.csproj` sets `AvaloniaNameGeneratorIsEnabled=false`. Avalonia's source generator auto-declares a class member per `x:Name` in XAML, and it collided (`CS0102`) with `MainWindow`'s own `GraphViewerHost` property once that property needed a name matching the `ContentControl`'s `x:Name="GraphViewerHost"`. The rest of the shell already reaches named controls through `FindControl<T>` (matching `DataLoadWindow`/`MessageDialog`), so disabling the generator project-wide removes the collision risk instead of threading around it per-control.
- `Foreman.Mac.Services.PresetResolver` and `ShellBootstrapper` (new): `PresetResolver.Resolve` mirrors `MainForm.GetValidPresetsList`'s validation (a `.pjson` only counts if its matching `.dat` also exists) and its `CurrentPresetName` fallback to `DefaultPreset` ("Factorio 2.0 Vanilla"). Upstream's `MainForm_FormClosing` is exactly `e.Cancel = !TestGraphSavedStatus()`; it never itself calls `Properties.Settings.Default.Save()`, since settings get saved at many other call sites (`NewGraph`, `ApplyLoadedGraphUiState`, the settings dialog) that don't exist yet at this phase. Without a save on close, the resolved preset name would never persist at all, so `ShellBootstrapper.BootAsync` wires `MainWindow.Closing` to `settingsService.Save(settings)` as a deliberate port-only addition.
